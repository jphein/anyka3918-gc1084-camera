Anyka AK3918 · GC1084 · Teruhal TC20

A $3 camera, opened all the way up

Local RTSP, PTZ, audio and Home Assistant control for a cheap Chinese IP camera — no cloud, no app — plus a reference for the firmware's undocumented internals, written down as it was found.

The speaker's volume control was documented as broken. It was never broken — it was never exposed. The value was welded shut at maximum: one immediate operand, compiled in, with no CLI flag and no environment variable to reach it.

From outside the binary those two look identical. A volume that will not change is a broken control and an unreachable one, and only the second has a fix — which is why the finding took disassembly rather than more experiments.

shippedmov r1, #6→ ak_ao_set_dac_volume(h, 6)
patchedmov r1, #1one byte, at offset 9356

Upstream's advice was to quieten the audio file instead. That cannot work: the firmware runs an always-on look-ahead compressor which normalises a quiet file straight back up. The DAC value reaches the hardware downstream of it — measured, then confirmed by ear.

Where a door is only half shut, it says so. No software route to the white LEDs is established; whether the hardware is even populated is a separate question nobody has answered with a meter. Those are different claims and the docs keep them apart.

Rules that earned their place

The most reusable thing here, and none of it is camera-specific.

  • Read the artifact before measuring the device. Every conclusion drawn from disassembly, source or /proc held. Nearly every conclusion drawn from an unvalidated measurement was overturned.
  • This firmware narrates itself. Twice the answer was a log line nobody had read. Run the binary in the foreground and read its output before inferring anything.
  • Establish what depends on a fault before repairing it. Three separate bugs turned out to be the only reason something worked.
  • Verify the effect, not the invocation. A 200, an exit code and an acknowledgement all mean parsed — never honoured.
  • A uniform result across varied inputs is a broken instrument. Not a conclusion. Several times a check returned the same answer for every input and looked like a clean pass.
  • Prose drifts, data doesn't. When a file holds both a table and a sentence summarising it, re-derive the sentence. Tables are usually measured; summaries are usually unsourced. At the observed frequency this is the dominant failure, not bad luck.
  • The stale half is the dangerous half. A doc gets edited where a new fact lands, not where the old one lives — so it ends up carrying a claim and its own refutation, both reading authoritative. Proximity is no protection: nobody re-reads the paragraph they just wrote.
  • Writing something down discharges the feeling of having handled it. A passage that is correct feels finished, which is why your own re-reads are least reliable on exactly the text you just wrote. Someone else reading it is the only mechanism that reliably works.
  • Printing evidence and requiring interpretation is not a guard. It fails precisely when the operator is in a hurry, which is when destructive tools get run. A guard should turn "an operator interprets output" into "a human answers a direct question about a named thing" — and the override must be documented with the refusal, or a correctly-working guard just sends someone to a tool that has none.

If you own one, read this part

It applies whether or not you ever flash anything.

A stock, un-modified camera runs a writable file service as root, on every interface, from boot. One line of the vendor's own rc.local:

/usr/bin/tcpsvd 0 21 ftpd -w / -t 600 &

All interfaces, writes enabled, served from the filesystem root, started as root. It does require a credential — anonymous login is refused, measured — but combined with an update path that flashes an uploaded archive without checking a signature, it is a complete root chain built entirely out of vendor parts.

The modification does not add this. It adds the off switch. The exposure is the vendor's, present on a camera straight out of the box, and the hacked firmware is what lets you turn it off. That direction matters: this is an argument for putting these cameras on an isolated VLAN, not an argument against opening them.

Honest limits

This is one person's camera, opened up and written down. Two things follow from that, and they are worth reading before you rely on any of it.

The repo is not the world. "Teruhal TC20" covers several board variants. The white LEDs are unwired on this one; the IR ring is dark on this one. Where a finding is unit-specific it says so, but treat a board difference as likely rather than surprising.

Verified is per path, not global. The docs distinguish what was measured from what follows by construction — including cases where something was confirmed by ear, then had its mechanism changed underneath it and is honestly marked as no longer covered by that test.
